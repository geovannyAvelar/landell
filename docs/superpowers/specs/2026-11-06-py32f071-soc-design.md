# SoC abstraction and PY32F071 core (sub-project 1 of 2)

## Goal

Run the F4HWN Fusion firmware for the UV-K5 V3 / UV-K1 (PY32F071) in landell,
selectable next to the existing DP32G030 (UV-K5 V1/V2) support.
Done when `landell-gui --soc py32f071 f4hwn.fusion.v5.4.0.bin --screenshot out.png`
shows the Fusion UI on the LCD, and the same image runs on the CLI.

Sub-project 2 (separate spec): radio models K5 V3 / K1 (key matrix, panel
layout, ADC wiring, `--radio`).

## Scope

In: SoC descriptor, memory map per SoC, VTOR, app-image boot, PY32F071
peripheral models needed to reach the main loop and drive the LCD, `--soc`
selection with auto-detection, tests.
Out: USB, audio, the K1/K5 V3 key matrix and panel (sub-project 2), flash
programming from firmware, apps loaded into the RAM overlay.

## Facts from the pinned firmware (armel/uv-k1-k5v3-firmware-custom, v5.4.0)

- Core Cortex-M0+, 128 KB flash at `0x08000000`, 16 KB SRAM at `0x20000000`.
- The app is linked at `0x08002800` (`Core/py32f071xb.ld`); a 10 KB bootloader
  before it has already configured a 48 MHz clock ("Bootloader has setup clock
  for us", `Core/Src/main.c`).
- Firmware uses the Puya LL drivers: direct register access. Peripherals seen:
  RCC, SYSCFG, PWR, FLASH, GPIO, SPI, USART, I2C, TIM, ADC, DMA, CRC, IWDG, RTC.
- LCD: ST7565 on SPI1, A0 on PA6, CS on PB2 (`App/driver/st7565.c`).
- External SPI flash (2 MiB) and I2C EEPROM exist on the board.

## Design

### SoC descriptor

```c
typedef struct dp32g030_soc {
  const char *name;                  /* "dp32g030", "py32f071" */
  uint32_t flash_base, flash_size;   /* backing store is the cpu's flash[] */
  uint32_t flash_alias;              /* extra base the flash is also seen at (0 = none) */
  uint32_t sram_base, sram_size;
  uint32_t image_base;               /* where a raw image is loaded */
  bool has_vtor;
  const dp32g030_region_t *(*region_find)(uint32_t addr);
  void (*reset)(dp32g030_cpu_t *c);  /* peripheral/bootloader hand-off state */
  struct { unsigned spi; uint32_t a0_port, a0_pin; } lcd; /* LCD tap config */
} dp32g030_soc_t;
```

- Public names keep the `dp32g030_` prefix (renaming is churn with no benefit).
- `dp32g030_cpu_t` gains `const dp32g030_soc_t *soc` and a PY32 peripheral
  state member; `flash[]` grows to 128 KB. Everything DP32G030-specific stays
  in place and unchanged in behavior.
- `dp32g030_cpu_new(fw, size)` keeps its signature and auto-detects the SoC
  (below). New: `dp32g030_cpu_new_soc(const dp32g030_soc_t*, fw, size)`;
  `const dp32g030_soc_t *dp32g030_soc_by_name(const char*)`.
- `bus.c` uses `soc->flash_base/size/alias` and `soc->sram_*` instead of the
  compile-time constants and asks `soc->region_find`.

### Boot

For `py32f071`: the image is copied to flash at `image_base` = `0x08002800`;
the vector table at that address provides SP and reset vector; `scs.vtor` is
set to `0x08002800`; `soc->reset` puts RCC/FLASH/PWR in the state the
bootloader leaves (PLL and HSI ready, 48 MHz, flash latency set). For
`dp32g030` nothing changes (image at 0, VTOR absent).

### VTOR

`scs.vtor` register at `0xE000ED08`, honored by exception entry only when
`soc->has_vtor`; on DP32G030 writes are ignored and reads return 0 (as now).
Vector fetch = `vtor + 4 * exception_number`.

### Auto-detection

`dp32g030_cpu_new` looks at the second word (reset vector) of the image: an
address in `0x08000000..0x0801FFFF` selects `py32f071`, anything else
`dp32g030`. `--soc auto|dp32g030|py32f071` (default `auto`) overrides it in the
CLI and `landell-gui`. The release image `f4hwn.fusion.v5.4.0.bin` is a raw app
image (SP `0x20004000`, reset `0x08002D49`, vector table at offset 0), so it is
loaded at `image_base`. Only raw app images are supported; images that include
the bootloader are out of scope.

### PY32F071 peripherals

- Bases and IRQ numbers come from the pinned firmware's CMSIS device header
  (`Drivers/CMSIS/Device/PY32F0xx/Include/py32f071xb.h`), copied into a table
  by the plan's first task and checked by a unit test.
- Rule: every peripheral starts as a plain register file; behavior is added
  only when running the firmware shows it is needed, each addition with a
  test. Known needs: GPIO (`MODER`, `IDR`, `ODR`, `BSRR`, `BRR`, `PUPDR`,
  `AFR`, ports A, B, C, F, with a `gpio_change` hook and host inputs like the
  DP32G030 model), RCC ready flags and clock-enable registers, FLASH `SR` not
  busy, SPI data register with the host `spi_xfer` hook and the LCD tap, USART
  TX hook and RX FIFO, ADC end-of-conversion with host-set inputs, I2C through
  the existing host hooks, SysTick/NVIC reused from the core.
- The LCD tap (`lcd.c`) is reused: `soc->lcd` says which SPI and which GPIO pin
  is A0 (PY32: SPI1, PA6; DP32G030: SPI0, GPIOB pin 9).

### External devices

If boot needs the external SPI flash or EEPROM, a minimal host-side model
(reads return `0xFF`, writes ignored) is added behind the existing host hooks
and enabled by default in the CLI/GUI. Anything beyond that is out of scope.

### CLI / GUI

- `landell --soc ...` and `landell-gui --soc ...`.
- GUI panel keeps the DP32G030 K5 matrix until sub-project 2; on `py32f071`
  the panel is still drawn but keys are not wired (documented).
- `--adc` defaults to the DP32G030 battery channel only when the SoC is
  `dp32g030`; for `py32f071` it is set in the board config in sub-project 2,
  and until then the ADC reads a documented default.

## Testing

- Existing suite stays green: the Python ctypes mirror (`tests/dp32g030.py`)
  is updated for the new `Cpu` layout; no DP32G030 test body changes.
- New unit tests: memory map and flash alias per SoC, VTOR vectoring
  (exception taken via a table at a non-zero VTOR), PY32 GPIO set/reset and
  input, SPI1 byte reaching the LCD tap with A0 on PA6, bootloader hand-off
  state, auto-detection and `--soc` override, rejection of an image too big
  for the SoC flash.
- A small hand-assembled PY32 image (like the existing `firmware/` test) that
  prints on USART and writes the LCD, run through the CLI.
- Integration with the real Fusion image is manual (the binary is not in the
  repo): run, screenshot, record the result in the ledger; each behavior
  discovered this way gets a regression test.

## Risks

- Exploratory: peripheral behavior is discovered by running the firmware; the
  scope is bounded by "reaches the main loop and draws the first LCD frame".
- The firmware may poll the external flash or EEPROM before drawing: covered by
  the minimal host model above.
- Without the PY32F071 reference manual, register semantics come from the HAL
  and firmware source; unknown behavior stays a plain register file.
- `cpu_t` grows (128 KB flash): memory per emulated cpu doubles; acceptable.

## Success criteria

- `meson test` stays green for DP32G030, plus the new PY32 tests.
- The Fusion v5.4.0 image reaches the main loop and writes a frame; the GUI
  screenshot shows the Fusion UI.
- `--soc` selects the chip; auto-detection picks the right one for both the
  egzumer/F4HWN v4.3 and the Fusion v5.4.0 images.

## Outcome notes (added after implementation)

- The "external devices" item turned out to be the board's EEPROM, which on the
  K5 V3 / K1 is emulated on an external **PY25Q16 SPI NOR flash** (SPI2, CS on
  PA3, DMA reads), not an I2C EEPROM. It is modeled as a 2 MiB flash (read,
  status, JEDEC ID, write enable, page program, sector/block/chip erase), with
  host access `dp32g030_extflash_set/get`. An I2C EEPROM model written first was
  reverted: the firmware never addresses one.
- Release v5.4.0 divides the battery reading by `gBatteryCalibration[3]` with no
  sanity fallback, so an erased calibration reads as a dead battery. The board
  defaults (`dp32g030_soc_defaults`) preset a factory-style block at flash
  `0x010140` and the battery on ADC channel 8; the GUI applies them.
- The BK4819 decoder was generalized to take its three pins from the SoC
  (PY32: CSN = PF9, SCL = PB8, SDA = PB9).
- The GUI keeps the DP32G030 key matrix off the PY32 pins (`Keypad::set_wired`).
